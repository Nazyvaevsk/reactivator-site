# Исправление отправки заявок — 29 октября 2026

## Причина и границы доказательства

Исходная локальная ветка: `main`, HEAD `4f32f7f`, рабочее дерево до работы чистое.
Пользователь предоставил строки production-журнала Timeweb:

```text
Failed to load external module sharp
Could not load the "sharp" module using the linux-x64 runtime
```

Это подтверждает отказ нативного декодера в production. В исходном коде
`applicationUploads.ts` импортировал sharp на уровне модуля, а API импортировал
`applicationUploads.ts`: сбой мог происходить до вызова POST и его try/catch.
Обработчик не мог вернуть свой JSON. Клиент безусловно вызывал response.json(),
поэтому пустой ответ превращался в `Unexpected end of JSON input`.
Это объясняет отсутствие и текста, и фото: Relay вызывается после проверки фото.

В package.json sharp был devDependency; Next подключает его также как optional.
Следовательно, один только omit=dev не доказывает причину отсутствия бинарника.
Точную причину его неработоспособности — исключённые optional-зависимости,
перенесённый/закэшированный node_modules, несовместимая libc/CPU — без конфигурации
контейнера установить нельзя. Патч исправляет упаковку и проверяет результат на
целевом runtime до приёма трафика.

## Изменения

- sharp 0.35.5 — прямая production-зависимость; версии остальных пакетов сохранены.
- В lockfile сохранены Linux x64 glibc/musl-пакеты sharp и libvips, без dev-маркеров.
- `.npmrc`: `include=optional`, необходимый для платформенных бинарников.
- `npm run check:sharp`: загрузка sharp, кодирование и полное декодирование JPEG,
  PNG и WebP с теми же ограничениями, что в API. Не печатает env, тела или stack.
- Проверка автоматически выполняется перед `npm run build` и `npm start`.
  Неисправный runtime завершается с ненулевым кодом, а не принимает заявки.
- Загрузка sharp перенесена внутрь валидации. Если запуск проверок был обойдён,
  API возвращает JSON 503; проверка изображений остаётся обязательной.
- Клиент проверяет статус, Content-Type, пустое/невалидное тело, success,
  submissionId и receipt. Таймаут 75 секунд охватывает fetch и чтение ответа.
  Форма разблокируется, сохраняет поля и прежний submissionId для повтора.
- Relay transport failures возвращают 502 с безопасной диагностикой. Нет
  автоматического повтора неоднозначной доставки в Telegram.
- В логах API: requestId, начало запроса, этап результата, HTTP-статус и длительность.
  В логах клиента: тип ошибки, статус, тип содержимого и проверенный requestId.

Телефоны, Origin/honeypot, rate limits, привязка и порядок фото, receipt-токены,
лимиты 10 фото/100 МиБ, проверка изображений и R2-защита сохранены. Максимум
multipart-запроса 12 МиБ, исходного файла на сервере 10 МиБ; клиент готовит до 8 МиБ.
На сервере чтение тела ограничено 15 секундами, каждый вызов Relay — 20 секундами.

## Получение исправления без потери работы

Исправление оформляется отдельным коммитом поверх `4f32f7f` и публикуется обычным
push в main с разрешения владельца. Повторно применять ранее экспортированный
патч к этой рабочей копии не нужно.

В другой чистой локальной копии получить исправление можно через
`git fetch origin main` и `git merge --ff-only origin/main`. Если есть локальные
изменения или расхождение истории, сначала сохранить работу и проверить diff;
не применять reset/force. Вместе переносить новые lib/scripts, `.npmrc`,
package.json и package-lock.json; не переносить node_modules или Windows `.next`.

Проверки из корня проекта:

```sh
npm ci --include=dev --include=optional
npm test
npx tsc --noEmit
npm audit
npm run build
npm run test:application:production
git diff --check
```

Публикация коммита в GitHub не является подтверждением исправления production.
Развёртывание и изменение настроек Timeweb требуют отдельного решения владельца.

## Timeweb: установка и запуск после разрешения владельца

1. Выбрать Node.js 22, выполнить чистую Linux-сборку из исходников. Отключить
   восстановление старого node_modules для первого развёртывания исправления.
   Убедиться, что сборка и runtime используют совместимые OS/CPU/libc.
2. Команда установки: `npm ci --include=dev --include=optional`.
   Dev-зависимости нужны для сборки; sharp теперь сохранится и после их удаления.
3. Команда сборки: `npm run build`. Она сначала выполнит sharp self-check.
4. Если платформа удаляет dev-зависимости, использовать
   `npm prune --omit=dev --include=optional`, затем `npm run check:sharp`
   именно в конечном runtime. Если runtime собирается отдельной стадией,
   устанавливать его зависимости через `npm ci --omit=dev --include=optional`.
5. Команда запуска: `npm start`. Она запускает prestart-проверку. Если платформа
   запускает `next start` напрямую или отключает lifecycle scripts, настроить
   `node scripts/check-sharp.cjs && next start` (с прежними параметрами порта).
   В финальный образ должны попасть `scripts/check-sharp.cjs` и `.npmrc`.
6. До переключения трафика убедиться в строке
   `sharp_runtime_check` с `ok:true`, `platform:"linux"`, `arch:"x64"`.
   При `ok:false` контейнер не готов: не обходить preflight и проверку фото.

Для Linux x64 sharp требует glibc >=2.28 или musl >=1.2.5 и совместимый CPU
с SSE4.2; Node >=20.9.0. При несовместимом образе нужен совместимый Linux runtime,
а не принудительное отключение валидации. Установка на целевой Linux автоматически
выбирает правильный бинарник; не надо фиксировать `--os=linux` в обычных скриптах
проекта или устанавливать Linux-бинарник поверх рабочей Windows-копии.
Источник требований: https://sharp.pixelplumbing.com/install/

Сессии/антидубли по-прежнему хранятся в памяти одного Node-процесса 15 минут.
Несколько реплик или перезапуск между фото требуют общего хранилища; патч не
обещает exactly-once после рестарта. На Timeweb проверить один процесс/реплику.

После разрешённого развёртывания нужна согласованная проверка одной тестовой
заявки в Telegram. Если ошибка сохранится, собрать без PII: UTC-время, HTTP-статус,
Content-Type, размер ответа, длительность, X-Request-ID, application_start/application
и application_relay_failed за ту же минуту; плюс архитектуру/libc/версию Node,
число реплик и результат check:sharp. Отсутствие application_start при 500 указывает
на сбой до POST; 413 без requestId — на возможный ingress-лимит; relay-message/photo
с 502 — на внешний участок. Это диагностические признаки, не окончательный вывод
без сопоставления журналов Timeweb и Worker.
