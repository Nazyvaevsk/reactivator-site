## 2. События и смысл ошибок Next.js

Владелец сообщил ошибки `The Server Reference ID did not match the expected format` со значениями `r2s` и `cachefn`, а также `Expected RSC response, got text/plain`. Они совместимы с некорректными/зондирующими запросами, несовпадением deployment/кэшей или неправильным ответом прокси. Сами по себе эти строки **не доказывают успешное выполнение кода или проникновение**. Отсутствие пользовательских Server Actions не гарантирует неуязвимость самого runtime Next.js.

В текущем приложении не найдены директивы `use server` и `use cache`. Не добавлялись фильтры, ломающие служебные RSC/Next-запросы или скрывающие ошибки вместо исправления runtime. Уязвимости зависимостей закрываются отдельным обновлением владельца, а не изменениями формы.

Две прежние мусорные заявки проходили старую валидацию: `+7 (375) 999-999999` содержит 13 цифр, `+79518888888` — 11. Раньше сервер допускал 10–15 цифр. Это не требовало обхода безопасности. По этим сообщениям нельзя установить человека, способ отправки или эксплуатацию runtime.

## 4. Совместимость и важные ограничения

- Не менялись дизайн, цены, SEO-структура, canonical URL, sitemap, public JSON и каталог с тысячами страниц. Нормальная валидация и невидимый honeypot не вводят CAPTCHA.
- Сохранены HMAC payload, формат клиентских ссылок, 24-часовой срок генератора, семидневные мастер-токены, Authorization и совместимость старых query-signatures. Проверки выполняются до R2. Просроченная, подменённая или подписанная для другого комплекта ссылка не даёт доступ.
- `sheet` берётся из существующей группы и проверяется на разрешённое имя; ключ R2 — из trusted metadata, не произвольного URL/пути клиента. `..`, пустые компоненты и неизвестные листы отклоняются.
- ZIP содержит те же плоские SVG-имена и байты, но использует STORE вместо синхронного compression. Исключительно большие реальные комплекты нужно проверить на новых лимитах; доступа к приватным объектам для измерения здесь нет. Переполнение даёт ошибку, не успешный неполный архив.
- Настоящие JPEG/PNG/WebP проверены offline. SVG, анимация, HEIC и прочие неподдерживаемые форматы теперь отклоняются с подсказкой. Это намеренное ограничение; пользователь может экспортировать JPEG/PNG. Не утверждается, что произвольный формат, ранее принятый только по MIME, доставлялся Telegram.
- Сессии загрузки/дедупликации хранятся только в памяти одного процесса, 15 минут, до 1000 записей, без байтов фото и открытых персональных данных. После рестарта или попадания на другой экземпляр продолжение может быть отклонено. Нужен один процесс либо отдельная реализация shared state/sticky routing перед масштабированием.
- Старые первые заявки без UUID принимаются. **Старые продолжения `sendMessage=false` без server receipt намеренно больше не принимаются**: сохранить этот обход совместимым нельзя. После будущего deployment владельцу нужно рекомендовать обновить старую вкладку формы. Новый frontend повторно использует тот же UUID и token при сетевом повторе.
- При неоднозначном ответе relay нельзя гарантировать exactly-once: downstream мог уже принять сообщение. Реализован консервативный отказ от автоматического повтора с предложением связаться с мастером. Надёжное повторение потребовало бы идемпотентности/статуса на стороне Worker/Telegram.
- Proxy-IP не привязывается к upload receipt: смена сети/NAT не обрывает обычную загрузку. Receipt сам является bearer-правом: не логировать и не передавать его посторонним.
- Не устранены архитектурные особенности подписанных ссылок: bearer-доступ, возможность переиспользования мастер-токена до истечения, отсутствие индивидуального отзыва/журнала оплат. Это действующая бизнес-логика, её не меняли без необходимости.
- На приватной странице аналитика исключена при прямом входе. Ранее загруженные сторонние скрипты при SPA-навигации могут оставаться в браузере. Не пересылать служебные ссылки, открывать их как отдельный переход; не включать сбор query strings/подписей в логах и аналитике. Полная изоляция приватного документа — отдельное архитектурное улучшение, здесь не заявлено исправленным.

## 6. Область аудита публичных маршрутов

Статические страницы `/`, `/about`, `/contacts`, `/technology`, `/works`, четыре страницы `/services/*`, `/services`, `/shop` не принимают серверных заявок сами; общий provider отправляет их в единственный API. Статические данные контактов/JSON-LD не строятся из пользовательского ввода. Markdown статей отображается React-экранированием, без исполнения MDX/raw HTML; ссылки ограничены HTTPS/внутренними путями.

`/articles/[slug]` использует список опубликованных материалов и `dynamicParams=false`. Публичные `/body-dimensions/[groupId]` и `/[sheet]` читают только allowlist публичного каталога через `lib/bodyDimensionsPublic.ts`, проверяют slug/номер и canonical; приватный index не используется для SEO. Произвольный клиентский путь не передаётся в `fs.readFile`.

API листов/ZIP проверяют HMAC до хранилища; нет local-original fallback или публичного URL оригинала. Конфигурация сохраняет SVG sandbox/CSP, nosniff/no-store/no-referrer/noindex и исключение private SVG из tracing. Приватный index описывает object keys, не содержит байтов оригиналов. Наличие noindex не является контролем доступа; им остаётся подпись.

Мастер-выдача — standalone-документ с nonce CSP, token во fragment, удалением fragment и явным POST. Подпись мастера не выдаётся публичной форме в ответе. Не найден прямой SQL/shell injection или SSRF через пользовательский URL в исследованной цепочке. Отсутствие таких путей не заменяет audit runtime/Worker/хоста.

## 7. Timeweb, Worker, R2 — ручной checklist до включения

### Timeweb App Platform

1. Зафиксировать ID приложения, оба привязанных домена, paused-state, исторический deployment/commit, число replicas/Node workers, команды build/start. Не включать приложение ради получения истории.
2. Проверить существующие runtime/error logs, access logs ingress, deploy/restart events. Для мусорных заявок 26.10.2026 10:39–10:40 Омск получить интервал **10:24–10:55 Омск = 04:24–04:55 UTC = 07:24–07:55 Москва**.
3. Для r2s/cachefn/RSC ошибок получить время, HTTP-метод, путь, статус, request ID, источник, число попыток и соседние ошибки. Не публиковать тела, Next action payloads, секреты или signed URLs.
4. Проверить доступные признаки успешного проникновения: неожиданные процессы/исходящие соединения, изменённые файлы/команды запуска/деплои, новые задания, неизвестные доступы в панели/SSH и изменения secret bindings. Отсутствие признаков в неполных логах не доказывает отсутствия компрометации.
5. Проверить bind-порт Node, cloud firewall/ingress и отсутствие прямого обхода gateway. Уточнить Caddy/Nginx/другую цепочку: старые документы ожидают Caddy, но фактический Timeweb ingress не известен из репозитория.
6. На существующем ingress установить, какой заголовок содержит реальный visitor IP и перезаписывается ли он. Default — правый `X-Forwarded-For`; опцию `CLIENT_IP_HEADER=x-real-ip` выбирать только после подтверждения. В staging проверить двух посетителей с разных сетей и невозможность spoofing. Заголовки не являются аутентификацией.
7. Подтвердить один Node-процесс или обеспечить sticky/shared state до масштабирования. Проверить upstream body/idle/read timeout и ограничение тела не ниже 12 МиБ с учётом frontend-потока.
8. Проверить имена/наличие переменных, НЕ выводя значения: `MASTER_CHAT_ID`, `RELAY_SECRET`, `BODY_DIMENSIONS_ACCESS_SECRET`, `BODY_DIMENSIONS_ISSUE_SECRET`, `BODY_DIMENSIONS_BASE_URL`, `R2_ACCOUNT_ID`, `R2_ACCESS_KEY_ID`, `R2_SECRET_ACCESS_KEY`, `R2_BUCKET_NAME`; при наличии — `CLIENT_IP_HEADER`. Не хранить секреты в NEXT_PUBLIC-переменных.
9. Если есть признаки утечки/исполнения кода, считать все доступные процессу секреты потенциально раскрытыми: согласовать ротацию relay/бота/R2/HMAC и доступов платформы. Ротация HMAC аннулирует существующие ссылки. Не ротировать автоматически только из-за строки ошибки; сначала сохранить evidence и оценить риск.

### Cloudflare Worker

Исходники Worker отсутствуют: **проверка обязательна вручную**. Убедиться в constant-time либо эквивалентной корректной проверке server secret, разрешённом MASTER_CHAT_ID, allowlist методов sendMessage/sendPhoto, body/time/rate limits, отсутствии произвольного proxy/URL/chat, запрете `parse_mode` для пользовательского текста, сохранении `reply_markup` и `disable_web_page_preview`. Worker должен возвращать достоверные HTTP status и Telegram JSON с `ok`, не журналировать тела/секреты/ссылки. Проверить bot permissions и закрытость чата мастера.

### R2

Проверить приватность original bucket, отключённый public development URL, отсутствие публичного домена оригиналов, read-only server token только на нужный bucket, отдельные upload credentials. Preview bucket/домен может быть публичным по текущей архитектуре. Проверить объектные ключи, размер самых больших SVG/ZIP, отсутствие секретов в браузерном bundle. Подписанная ссылка другого комплекта не должна открывать чужой лист.

## 8. Команды получения исторических журналов (только чтение)

На действующем сервере, если есть SSH, владелец может определить способ запуска:

```bash
date --iso-8601=seconds
timedatectl show -p Timezone
systemctl list-units --type=service --all --no-pager | grep -Ei 'caddy|nginx|reactivator|node|pm2|docker'
sudo ss -ltnp
systemctl show APP_UNIT -p FragmentPath -p MainPID -p StandardOutput -p StandardError
docker ps --format 'table {{.Names}}\t{{.Image}}\t{{.Ports}}'
```

Заменить APP_UNIT реальным именем; отсутствующие команды не устанавливать ради расследования. Caddy runtime может находиться в journald, access log — только при включённом logging и в пути из конфигурации (часто /var/log/caddy). Nginx обычно использует /var/log/nginx/access.log и error.log, но реальные пути определяются конфигурацией. Node systemd пишет в journald либо настроенные stdout/stderr-файлы; Docker/PM2 имеют собственный log backend. Не считать stdout приложения HTTP access log.

```bash
sudo journalctl -u caddy --since '2026-10-26 04:24:00 UTC' --until '2026-10-26 04:55:00 UTC' --utc --no-pager -o cat
sudo journalctl -u APP_UNIT --since '2026-10-26 04:24:00 UTC' --until '2026-10-26 04:55:00 UTC' --utc --no-pager -o short-iso-precise
docker logs --timestamps --since '2026-10-26T04:24:00Z' --until '2026-10-26T04:55:00Z' CONTAINER
```

Для стандартного JSON access log Caddy на локально скачанной копии:

```bash
jq -Rrc 'fromjson? | select(type == "object") | select(.request.method == "POST") | select(((.request.uri // "") | split("?")[0]) == "/api/send-telegram") | select(.ts >= 1792988640 and .ts <= 1792990500) | {utc:(.ts|floor|todateiso8601),peer_ip:.request.remote_ip,client_ip:.request.client_ip,host:.request.host,status:.status,duration:.duration,bytes_read:.bytes_read,user_agent:.request.headers["User-Agent"],origin:.request.headers.Origin}' caddy-access.jsonl
```

Это не фильтр для текстового error log. Пустая выборка требует проверки формата, даты, ресурса и архивов. Для стандартного Nginx access log предварительно:

```bash
zgrep -hE '"POST /api/send-telegram(\?[^ ]*)? HTTP/' access.log access.log.1 access.log.*.gz
```

Указать существующие имена и отдельно отобрать нужное время с учётом смещения строки (`+0000`, `+0300` и т.д.). Сохранять копии, не очищать/перемещать оригиналы. Фильтровать статусы, IP, время, размер, количество попыток; один POST может быть одним из десяти фото. Отсутствие предшествующих GET, необычный User-Agent и разрешённый Origin не доказывают ни бота, ни браузер. IP за NAT не идентифицирует человека. Access logs обычно не содержат имён/телефонов — сопоставление с Telegram по времени может быть неоднозначным.

Для истории до патча искать текущие старые сообщения `Relay sendMessage failed, HTTP status:`, `Relay sendPhoto failed, HTTP status:`, `send-telegram request failed`. Для нового патча добавляются безопасные метаданные request ID. Ошибки валидации старого кода отдельно не записывались. Если access logs не велись/удалены, исторические IP и попытки задним числом не восстановить. Если Timeweb предоставляет только runtime/build logs, запросить access logs управляемого ingress у поддержки, указав оба домена, ресурс и UTC-интервал. Не отправлять поддержке полные env/Docker inspect, signed URLs и request bodies.
